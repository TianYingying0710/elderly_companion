# 老人端前端解耦与重复代码整理设计

日期：2026-10-26

## 1. 意图

在不改变现有界面、演示功能、技术栈和三端独立边界的前提下，清理老人端前端中的重复样式，拆分职责过重的页面和状态控制器，为下一阶段接入真实后端接口降低修改范围和回归风险。

本轮是结构整理，不新增业务能力。完成后用户看到的页面、演示数据、导航方式、一键求助演示流程和 Android 行为应与当前版本一致。

## 2. 目标

- 清除当前未使用的桌面预览 CSS 和重复覆盖规则。
- 将 `AccountPage.vue` 中互不相关的业务页面拆为独立组件。
- 将课程、家人、设备、消息、服务、求助等类型从 `demo/data.ts` 中分离。
- 让公共组件依赖业务中立类型，不直接依赖模拟数据模块。
- 将导航、演示模式、聊天、求助和健康检查职责拆分为独立组合函数。
- 保留轻量 `useElderApp` 作为组装入口，避免一次性改变所有页面调用方式。
- 减少页面直接修改全局状态的情况，业务状态变化由明确方法完成。
- 明确 Android 构建环境和调试签名检查，避免再次出现覆盖安装签名冲突。
- 保持三个应用独立，只通过 API 契约协作。

## 3. 非目标

- 不新增数据库、表、迁移、初始化或填充脚本。
- 不新增或下载业务数据。
- 不接入真实 AI、语音、视频、通知、电话、定位或硬件。
- 不新增真实认证、家人绑定、授权或求助服务。
- 不开发监护人端和社区端业务页面。
- 不修改现有 API 契约，不新增后端业务接口。
- 不引入 Pinia、Vue Router 或其他依赖。
- 不为了消除重复而让三个应用跨端引用内部源码。
- 不把 JDK、Android SDK、Gradle、调试密钥或机器绝对路径放入仓库。

## 4. 约束与反目标

- 当前演示版必须持续可运行，不能以“架构更整洁”为代价改变交互或视觉结果。
- 模拟数据继续集中保存并带有明显演示标识，关闭演示模式时必须清除模拟状态。
- 页面不得直接访问数据库、模型服务、设备或其他应用源码。
- 重构过程不得用固定成功响应冒充真实能力。
- 不做一次性大改；每一阶段必须可独立验证和回退。
- 不能把当前可控的三端重复代码抽成新的运行时耦合。

## 5. 已考虑方案

### 方案 A：表面清理

只删除重复 CSS 并拆分 `AccountPage.vue`，保留统一大状态对象。改动较少，但真实 API 接入时仍需再次拆分状态和数据类型。

### 方案 B：分层整理（已选择）

清理 CSS、拆分页面、分离业务类型、拆分组合函数，并保留兼容性的组装入口。它能解决已发现的主要耦合，同时不引入新框架，适合当前第一版演示阶段。

### 方案 C：全面架构升级

引入 Vue Router、Pinia、Repository 层和完整模块化目录。长期能力更强，但会增加依赖和回归范围，不符合当前快速完成第一版的目标。

## 7. 页面拆分

`AccountPage.vue` 拆为以下页面：

- `AccountHomePage.vue`
- `SettingsPage.vue`
- `ProfilePage.vue`
- `DevicesPage.vue`
- `FamilyPage.vue`
- `FamilyDetailPage.vue`
- `RequestsPage.vue`
- `MessagesPage.vue`
- `MessageDetailPage.vue`
- `ChatHistoryPage.vue`
- `ServicePage.vue`
- `ServiceDetailPage.vue`

`App.vue` 继续负责顶层外壳、底部导航、全局反馈、模态框和原生返回事件。它根据当前页面选择具体组件，不在本轮引入路由库。

每个页面只接收其渲染所需的数据和操作。为控制迁移风险，第一阶段允许通过 `useElderApp` 返回的分区对象传递；最终不再让所有页面任意修改整个 `state`。

## 8. 状态与操作边界

- `useNavigation`：当前页面、历史栈、选中项、前进和返回。
- `useDemoMode`：演示开关、模拟数据克隆、关闭演示时清理状态。
- `useChat`：消息、草稿、本地发送提示和历史会话载入。
- `useSos`：求助状态机、演示记录、取消和进度切换。
- `useHealth`：只负责 `/health` 检查状态。
- `useElderApp`：组装以上模块，并向顶层应用提供稳定接口。

页面不得直接执行求助状态跳转、权限切换或演示模式清理等业务变化。字体大小、搜索词等纯界面状态可以保留简单绑定，但优先通过明确方法修改。

## 9. 数据与接口边界

`demo/data.ts` 只提供符合业务类型的虚构数据，不再定义公共组件类型。`CourseList` 改为接收 `Course[]`，其他页面同样依赖业务类型而不是 `DemoData` 的推导类型。

真实接口仍统一通过 `src/api/client.ts`。本轮只有 `/health` 可调用，模拟数据不会伪装成 API 响应。未来真实数据源接入时，页面和组件无需知道数据来自演示模块还是 API。

## 10. 样式整理

- 先根据当前模板建立实际使用选择器清单。
- 删除 `.layout`、`.aside`、`.steps`、`.chatblank` 等未被当前页面使用的预览样式。
- 合并 `.app`、`body`、`.categories`、`.hero` 和 `.landscape` 等重复定义。
- 将基础、布局、组件和页面样式拆开，由 `main.ts` 按固定顺序导入。
- 不改变颜色、字号、卡片尺寸、底部导航和大字模式的视觉结果。
- 以 Android 模拟器截图和关键页面人工对照作为视觉回归依据。

## 11. 环境解耦

- `.env.local` 和 `android/local.properties` 继续由 `.gitignore` 排除。
- 构建脚本只接受环境变量或参数，不写死本机路径。
- Android 构建前检查 Java、SDK、Gradle 用户目录和调试密钥是否存在。
- 普通 `android:verify` 只验证同步和构建，不依赖已启动的模拟器或连接设备。
- 另设显式设备验收步骤：APK 生成后输出签名摘要；覆盖安装前与模拟器已安装包签名比较，不一致则停止并说明，不自动卸载应用。
- 不复制密钥到仓库，也不修改其他虚拟机。

## 12. 三端重复代码处理

三个 FastAPI `main.py` 和两个小程序 API 客户端存在结构性重复，但目前代码量小，并且独立部署是明确要求。本轮不抽取它们的运行实现。

`code4-shared` 继续只保存稳定、业务中立的契约。只有当多个端出现稳定且完全一致的请求或响应模型时，才考虑把模型契约放入共享模块；不共享页面、状态、服务实现或环境配置。

## 13. 实施顺序

1. 补充结构保护测试，记录现有页面、导航、演示开关、求助状态和健康检查行为。
2. 提取业务类型，并解除公共组件对 `DemoData` 的依赖。
3. 拆分 `AccountPage` 和服务页面，保持顶层导航不变。
4. 拆分组合函数，由 `useElderApp` 继续提供兼容入口。
5. 清理和拆分 CSS，逐页进行 Android 视觉对照。
6. 增加 Android 构建环境预检，并增加独立的设备签名与覆盖安装验收步骤。
7. 运行完整测试、类型检查、Web 构建、Android 构建和模拟器验收；没有连接设备时仍可完成普通构建验证。

## 14. 验收标准

- 现有 11 项测试继续通过，并补足拆分后的模块测试。
- TypeScript 类型检查和 Vite 生产构建通过。
- Android Debug APK 构建、签名检查和覆盖安装通过。
- 首页、陪伴、教学、我的、设置、家人、设备、服务、消息、求助页面均可访问。
- Android 返回键、演示开关、大字模式、教学筛选、聊天草稿和求助状态机行为不变。
- 关闭演示模式后不显示或保留模拟业务状态。
- 通用组件不再导入 `demo/data.ts`。
- 三端不存在跨应用内部源码引用。
- 当前模板未使用的旧 CSS 被移除，重复选择器得到合并。
- 仓库中不存在调试密钥、SDK、JDK、Gradle 缓存、数据库或新增业务数据。

## 15. 实施者可自行决定的细节

- 业务类型在 `domain.ts` 内的具体排序和命名。
- 页面组件的目录内索引文件是否需要建立；没有明显收益时不建立。
- CSS 四个文件之间的精确归属，以避免循环覆盖和保持视觉一致为准。
- 单个纯展示页面使用 props 还是窄接口对象，以最少暴露状态为原则。
