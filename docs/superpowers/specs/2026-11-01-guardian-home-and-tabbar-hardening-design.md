# 监护人端首页与主导航加固设计

日期：2026-11-01

## 意图

修复监护人端微信小程序中底部主导航切换迟缓、点击区域偏小，以及首页健康趋势折线覆盖标题的问题。保留未来硬件接入所需的健康趋势结构，但明确当前内容是虚构演示数据，不新增真实监护、设备或提醒能力。

## 目标

- 四个一级页面改用微信小程序正式的 `tabBar` 路由语义和 `switchTab`，同时保留当前自定义视觉风格。
- Tab 页面首次显示后保留页面实例；消息页再次显示时保留用户已选的筛选项，其他页面尽量保留滚动位置。
- 每个 Tab 的有效触控区域至少覆盖 88rpx 高度，并提供即时按压反馈。
- 导航失败时给出可见但非业务成功的错误提示。
- 保留“近 7 天健康趋势”及详情箭头，作为未来硬件数据的稳定展示位置。
- 本轮趋势只展示“近 7 天每日平均静息心率”，补齐日期、单位和演示标识，并修复 canvas 尺寸与溢出。
- 移除趋势卡片中没有业务含义的黄色铃铛。
- 首页健康概况与趋势明确标注为演示数据。

## 非目标

- 不接入硬件、设备 SDK、真实健康数据、数据库或监护人业务后端。
- 不实现健康趋势详情页，不让箭头产生虚假的成功业务能力。
- 不处理 AI 建议卡片及其箭头；留待下一轮设计详情能力。
- 不处理“我的”页面菜单；留待后续逐项确定真实目标页面。
- 不实现提醒完成状态，不为提醒右侧空心圆制造仅存在于内存的假闭环。
- 不修改监护人后端；后端仍只有 `/health`。

## 方案比较

### 方案 A：继续使用 `redirectTo`

扩大点击区域并增加反馈，改动最小，但每次切换仍关闭当前页并创建目标页，页面状态与生命周期不符合一级主导航语义。

### 方案 B：正式 `tabBar` + `switchTab`（选定）

在 `pages.json` 注册四个一级 Tab，导航统一走 `switchTab`，使用单一共享实现维持当前视觉。该方案符合 uni-app 与微信小程序的正式主导航机制，能够在首次加载后复用 Tab 页面并降低重复创建成本。

### 方案 C：预加载现有页面

保留错误的路由模型再叠加预加载，复杂度较高，并不能解决触控面积、状态语义和导航失败反馈，不采用。

## 页面与交互设计

### 底部主导航

- 页面：老人画像、AI 建议、消息、我的。
- 点击非当前项：立即出现按压反馈，然后调用 `switchTab`。
- 点击当前项：不重复跳转，但仍有按压反馈。
- 快速重复点击：同一时刻只允许一次导航，结束后解除锁定。
- 导航失败：解除锁定并显示“页面切换失败，请重试”；不静默失败。
- 触控区域包含图标、文字及安全区上方的整块 Tab 区域；底部系统安全区只负责留白，不承载点击。

### 健康趋势

- 标题：`近7天健康趋势`。
- 指标：`每日平均静息心率`。
- 单位：`次/分`。
- 显示七个日期标签与明确标注的虚构演示值。
- 当前数据只用于 UI 演示，未来硬件接入时通过稳定 ViewModel 替换数据来源，不让页面直接依赖设备原始字段。
- canvas 使用明确的 CSS 宽高和绘图缓冲区尺寸；绘图内容裁剪在图表区域内，不得覆盖标题、演示标识或详情箭头。
- 删除黄色铃铛。

### 提醒区

- 本轮仍为只读展示。
- 移除右侧无功能的空心圆，避免暗示可完成提醒。
- 保留提醒区标题和未来详情入口箭头，但本轮不创建详情页；若用户点击规划入口，只能给出“功能建设中”提示，不能改变数据或伪造成功。

## 分层与耦合约束

- Tab 路由定义保持单一真源；页面不得各自复制 URL 或导航判断。
- Tab 组件只负责渲染与发出导航请求，不依赖 mock、健康数据或页面业务。
- 心率演示序列从页面脚本中移出，使用明确的展示模型；页面只负责绘制，不引入硬件 SDK 字段。
- 不新增跨应用导入，不修改 `code1-elder`、`code3-community` 或 `code4-shared`。
- 不把导航错误、设备未接入或演示数据包装成后端成功响应。

## 验证

- 先补失败测试，覆盖四个 Tab 路径、`switchTab`、当前项不重复跳转、导航锁与失败反馈。
- 覆盖首页不再包含黄色铃铛和提醒空心圆，趋势具有指标、单位、日期和演示标识。
- 运行监护人端 `npm test`、`npm run type-check`、`npm run build:mp-weixin`。
- 在微信开发者工具实测四个 Tab 的首次与再次切换、消息筛选状态保留、快速连点、首页折线不越界。
- 最终确认 Git 只包含本设计批准范围内的文件。
